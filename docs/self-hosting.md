# Self-hosting Fanfare

(German: [self-hosting.de.md](self-hosting.de.md).)

## 1. Choose your setup

| Setup | Who it is for | Needs |
| --- | --- | --- |
| **Demo online** | Trying it, or a phone with internet | Nothing. |
| **Laptop with `fanfare-local`** | The coach on match day: no internet, speakers on the laptop, phone remote | Python 3.9+, the `fanfare-local` package. The only setup with the phone remote. |
| **Docker** (below) | One IT-savvy member who wants Fanfare on a PC or home server | Docker or Podman |
| **Raspberry Pi appliance** ([deploy/raspberry-pi/README.md](../deploy/raspberry-pi/README.md)) | A club house: a Pi next to the router serves `http://fanfare.local` to every phone on the club Wi-Fi and updates itself | Raspberry Pi 4 or 5 (2 GB is enough), SD card, Ethernet |
| **Behind your existing proxy** (sections Caddy, Traefik, Nginx Proxy Manager below) | A club that already runs a server with a reverse proxy and a domain | A proxy you know |

Fanfare Studio (the local voice server) is **not recommended on a Raspberry Pi**: voice generation is too slow
for comfortable preparation. Prepare the voices on a laptop and export and import them (`docs/local-voice-server.md`).

## 2. What any host must do

Fanfare is a folder of static files (`dist/`). Any web server works if it does all of this. The Docker image
does it already (`docker/fanfare.caddy`), and so does any proxy in front of that image: it passes the headers through.
Only when you serve `dist/` yourself (no Fanfare container) do these rules become your job:

- [ ] Serve `dist/` as static files. Hosting under a sub-path works (the site uses relative URLs, `base: './'`; the service worker scope follows the folder).
- [ ] MIME types: `.wasm` as `application/wasm`, `.mjs` and `.js` as JavaScript, `.webmanifest` as `application/manifest+json`.
      Do **not** compress `.wasm`, `.onnx`, `.data` or media.
- [ ] Send the **Content-Security-Policy header** with exactly the value of the `<meta>` tag in `index.html`:
      `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self' http://localhost:* http://127.0.0.1:*; media-src 'self' blob:; img-src 'self' data: blob:; style-src 'self' 'unsafe-inline'; worker-src 'self' blob:; object-src 'none'; base-uri 'self'`
- [ ] `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`.
- [ ] `Cache-Control: no-cache` for `index.html` and `sw.js` (never stale); a long cache (`public, max-age=31536000, immutable`) only for the hashed files under `assets/`.
- [ ] **Access logs off, or IP addresses anonymised** (GDPR: no visitor addresses, paths or User-Agents stored). Every example here has them off. If a proxy
      or your host writes its own log, that log is your responsibility.
- [ ] No request to any other origin: the page makes none, and the CSP forbids them.

`tests/hosting/validate.sh` checks all of this against the Traefik and nginx examples; `tests/docker/smoke.sh` against the image.

## Docker

Fanfare is a static website. This repository ships a `Dockerfile` (builds the site, serves it with
Caddy, no Node in the final image) and a `compose.yaml`. Nothing leaves the browser, and the server
**keeps no access logs** (no visitor addresses are stored).

The Docker setup serves the app only. The **phone remote** ("soundboard mode") is a small relay inside
`fanfare-local.py`; it needs `fanfare-local` on the laptop and does not work from this container.

## Quick start

```sh
git clone <this repository> fanfare && cd fanfare
docker compose up -d --build
# open http://localhost:8080
```

The first build downloads about 660 MB of voices (kept in a build cache, so later builds are fast)
and takes several minutes. The port is published on `127.0.0.1` only: this computer, nobody else.

- **Port 8080 already taken?** `FANFARE_PORT=8090 docker compose up -d` (or put `FANFARE_PORT=8090` in a
  file called `.env` next to `compose.yaml`).
- **Podman:** `podman compose up -d --build` or `podman-compose up -d --build` work the same way.
  The build cache mount (`RUN --mount=type=cache`) is supported by Buildah; if your version rejects it,
  delete that one option in the `Dockerfile`. The image then downloads the voices on every build.
- Check: `docker compose ps` shows `healthy`.

## HTTPS without a public domain: risks and steps ("HTTPS on the LAN", optional)

This section applies to every setup in this manual that uses a local certificate: Docker, Caddy, Traefik, Nginx
Proxy Manager and the Raspberry Pi appliance. **Self-signed HTTPS is opt-in everywhere and never the default.**
There is exactly one local CA route: `fanfare-local.py --issue-certs` (a CA limited by name constraints to local
addresses). Do not use `tls internal` of Caddy, a CA generated by Traefik, or mkcert for Fanfare: their CAs are not
name-constrained. The only other thing Traefik offers is its built-in default certificate: a browser warning on
every device and nothing to install (then offline mode and the microphone still do not work on phones).

On `http://` a phone on your Wi-Fi can use Fanfare, but not offline mode or the microphone (they need
https). **Plain HTTP is the default and needs no certificate.** HTTPS is opt-in and uses the **same
name-constrained local certificate authority (CA) as `fanfare-local --lan --https`**; the container
never creates a CA itself. Read the risks first (the container prints the same list):

1. Phones that trust this certificate trust everything signed with this laptop's key. Thanks to name constraints this is limited to local network addresses, but that includes routers, NAS drives and smart-home devices on that Wi-Fi.
2. The key is stored unencrypted on this computer. Anyone with access to this computer or user account could create fake certificates for local devices. Only use this on a computer you trust.
3. Remove it when you no longer need it: run start-fanfare with --forget-ca on the laptop (or: python3 fanfare-local.py --forget-ca), and remove the certificate on each phone (Android: Settings > Security > Encryption & credentials > User credentials; iPhone: Settings > General > VPN & Device Management > profile > Remove).
4. Without HTTPS, Fanfare still works over Wi-Fi, but phones can't use offline mode or the microphone.
5. Simpler alternatives: the online demo on the phone, or Fanfare directly on the laptop with the speakers. No certificate is needed for those.

The CA is limited to private network addresses, `localhost` and `*.local` (10/8, 172.16/12, 192.168/16,
100.64/10, 127/8). Use a `.local` name such as `fanfare.local` (your router or computer must resolve it)
or the computer's LAN address, not an arbitrary name like `fanfare.lan`.

**1. Make the certificate** on the computer that runs Docker (Python 3.9+ with `openssl` or
`pip install cryptography`). It asks you to type `yes` the first time (no terminal: add `--accept-ca-risk`):

```sh
python3 scripts/fanfare-local.py --issue-certs ./certs --name fanfare.local --ip 192.168.1.20
```

This writes only `server.crt`, `server.key` (private), `hosts.txt` and `expires.txt` to `./certs`; the CA
and its key stay in your user config folder (`~/.config/fanfare-local/`). It prints the CA fingerprint, the
phone steps and the expiry date (825 days at most). Without Python on the host, use a throw-away container
(the CA then lives in `./ca`, keep that folder private; delete it to remove the CA):

```sh
docker run --rm -it -v "$PWD/scripts:/s:ro" -v "$PWD/certs:/out" -v "$PWD/ca:/ca" python:3.12-alpine \
  sh -c 'apk add -q openssl && python3 /s/fanfare-local.py --config-dir /ca --issue-certs /out --name fanfare.local'
```

(This container route is untested. Podman: the same, with `podman run`. The container runs as root inside, so with Docker run
`sudo chown -R "$USER" certs ca` afterwards. It installs `openssl`; alternatively `pip install cryptography`.)

**2. Start Fanfare with the HTTPS override** (publishes port 8443 on the LAN; the risk flag is your yes):

```sh
FANFARE_HOST=fanfare.local FANFARE_ACCEPT_CA_RISK=1 \
  docker compose -f compose.yaml -f compose.https.yaml up -d
```

The certificate folder is `./certs`, or `FANFARE_CERTS_DIR`. The port is `FANFARE_HTTPS_PORT` (8443);
`FANFARE_HTTPS_BIND` limits the address. Without `FANFARE_ACCEPT_CA_RISK=1` only HTTP is served. The
container refuses to start HTTPS when the certificate files are missing, when `FANFARE_HOST` is not covered
by the certificate (`hosts.txt`), or when the certificate has expired, and warns 30 days ahead. In this mode the
container runs as **your own user** (all capabilities still dropped), because the key is private to you. With
rootless Podman that is the default. With plain Docker set it explicitly:

```sh
FANFARE_UID=$(id -u) FANFARE_GID=$(id -g) FANFARE_HOST=fanfare.local FANFARE_ACCEPT_CA_RISK=1 \
  docker compose -f compose.yaml -f compose.https.yaml up -d
```

If the container cannot read the key it stops with a message saying so.

**3. Trust the CA on each phone.** Send `~/.config/fanfare-local/ca.crt` (the certificate, never `ca.key`) to
the phone yourself and install it as a CA certificate (Android: Settings > Security > Encryption & credentials >
Install a certificate > CA certificate; iPhone: open the file, install the profile, then Settings > General >
About > Certificate Trust Settings > switch it on). Compare the SHA-256 fingerprint with the one printed by
`--issue-certs`, then open `https://fanfare.local:8443`. This computer itself can keep using
`http://localhost:8080`, which needs no certificate.

**Renewing:** run the `--issue-certs` command again before the expiry date (it makes a fresh certificate once
the old one is about 700 days old; `--issue-certs` and `fanfare-local --lan --https` share the same server
certificate, so re-issuing from either is harmless), then `docker compose ... up -d --force-recreate`.

### Removing the certificate authority

```sh
docker compose -f compose.yaml -f compose.https.yaml down -v
python3 scripts/fanfare-local.py --forget-ca       # deletes the CA and its keys (add --yes to skip the question)
rm -rf certs                                        # (and ./ca if you used the container)
```

Then remove the certificate on each phone (Android: Settings > Security > Encryption & credentials > User
credentials > fanfare-local CA > Remove. iPhone: Settings > General > VPN & Device Management > fanfare-local CA >
Remove Profile).

### A real domain (Let's Encrypt)

If the machine is reachable from the internet and a domain points at it, Caddy can get a public
certificate instead: `FANFARE_HOST=club.example.org FANFARE_ACME=1 docker compose up -d`, publishing
`80:8080` and `443:8443` (the commented lines in `compose.yaml`). Caddy then contacts Let's Encrypt
to obtain and renew the certificate (Let's Encrypt only, no fallback issuer). That is the one outgoing connection; the app itself never contacts
anyone. Not the default and not tested here.

## Behind your own reverse proxy

All examples serve plain HTTP by default, have **no access log**, and keep the Fanfare container as the only
place that knows MIME types and cache rules. Ready-to-use files are in `deploy/`; `tests/hosting/validate.sh`
runs them (`caddy validate`, `nginx -t`, and a Traefik and an nginx proxy against the real image, checking
CSP, `nosniff`, `Referrer-Policy`, `application/wasm`, `no-cache`, long cache and the absence of log lines).

### Caddy (standalone or in front)

`deploy/caddy/` has three Caddyfiles. Copy `docker/fanfare.caddy` next to them (it holds the headers, MIME types
and cache rules) and set its `root * /srv` line to the folder that holds `dist/`.

- `Caddyfile`: plain HTTP on `:8080`. Put it behind another proxy, or open it on the LAN.
- `Caddyfile.domain`: a real domain (`FANFARE_HOST=club.example.org`) with automatic Let's Encrypt (pinned to Let's Encrypt, no
  fallback issuer). The one outgoing connection of the whole setup is Caddy to Let's Encrypt.
- `Caddyfile.local-ca`: opt-in, with the risks below: certificates from `fanfare-local.py --issue-certs` loaded with
  `tls /etc/caddy/certs/server.crt /etc/caddy/certs/server.key`. Caddy makes no CA of its own.

Access logs: Caddy writes none unless a site block has `log`. The global `log { exclude http.log.error }` keeps even
error lines (client address, User-Agent) out.

### Traefik

`deploy/traefik/` holds `compose.yaml`, `traefik.yml` (static), `dynamic.yml` (router, service, header middleware)
and `dynamic-tls.yml`. Traefik reads **files**: it needs no Docker socket.

```sh
cd deploy/traefik && docker compose up -d --build          # then http://fanfare.local/ (edit Host() in dynamic.yml)
```

- **Headers:** the `fanfare-headers` middleware in `dynamic.yml` sets the CSP (identical to `index.html`),
  `nosniff`, `Referrer-Policy: no-referrer` and `Permissions-Policy`. The container's own `Content-Type` and
  `Cache-Control` pass through unchanged.
- **Access log:** there is no `accessLog` section, so Traefik writes none. `checkNewVersion` and
  `sendAnonymousUsage` are off (no call home). The log level is `WARN`.
- **Docker labels** (`compose.labels.yaml`): shown as an example only. Labels need the **Docker socket** inside Traefik,
  and whoever controls that container controls Docker, which is root on the host (`:ro` does not help). If you want
  labels, put a read-only socket proxy in between; the file provider above avoids the problem and is what the
  Raspberry Pi appliance uses.
- **TLS, real domain:** add a `websecure` entry point (already in `traefik.yml`), publish port 443 and a
  `certificatesResolvers` entry with the HTTP or DNS challenge of Let's Encrypt in `traefik.yml`, then add `tls: {certResolver: ...}` to the router.
  Not tested here.
- **TLS, self-signed, three levels:** (a) Traefik's built-in default certificate: a browser warning on every device,
  nothing to install, but then no offline mode or microphone on phones; (b) a file-provider certificate from the
  name-constrained local CA: make it with `python3 scripts/fanfare-local.py --issue-certs ./certs --name fanfare.local --ip 192.168.1.20`,
  uncomment the `dynamic-tls.yml` and `./certs` lines in `compose.yaml`, publish `443:443`. Read the risks below first.

### Nginx Proxy Manager

`deploy/nginx-proxy-manager/README.md` has the click path; the essentials:

1. **Proxy host:** domain `fanfare.local` or your domain; scheme `http`; forward host name = the Fanfare container (same Docker network) or its IP,
   forward port `8080`; WebSockets are not needed. Leave "Cache Assets" **off** (the container sets the cache rules).
2. **Advanced > Custom Nginx Configuration:** paste `deploy/nginx-proxy-manager/custom.conf`. It turns the access log off for the
   host (`access_log off;`), replaces the four security headers once (no duplicates, `always`) and sets the CSP identical to `index.html`.
3. **SSL:** with a real domain, "Request a new SSL certificate" (Let's Encrypt). Without one, do not let NPM make anything
   self-signed: use "Custom" and upload the `server.crt` and `server.key` made by `fanfare-local.py --issue-certs`. The risks below apply.
4. **Logs:** NPM's own error log can still contain client addresses when a request fails; shorten its retention (logrotate) or accept it.
   `access_log off;` in the snippet removes the access log of that host.

### Raspberry Pi appliance

A Pi 4 or 5 (2 GB is enough) next to the club-house router serves `http://fanfare.local` to every phone on the club Wi-Fi,
updates itself, and stores no visitor data. The step by step guide for non-experts, including the Raspberry Pi Imager
settings, is `deploy/raspberry-pi/README.md` (German: `README.de.md`). In short: copy this folder to the Pi and run

```sh
sudo ./deploy/raspberry-pi/install.sh            # add --dry-run to only print the steps
```

It installs and configures unattended-upgrades (security and stable updates, reboot window 04:00, unused dependencies removed),
Docker from the Debian / Raspberry Pi OS repositories (`docker.io`, and `docker-compose-v2` or `docker-compose`; no `curl | sh`), avahi (`fanfare.local`),
caps journald and uses the `local` Docker log driver with a small size (SD-card wear), builds the image from the checkout (or
loads one with `--image-tar`) and starts Traefik + Fanfare from `deploy/raspberry-pi/compose.yaml` on port 80. A weekly
systemd timer (`fanfare-update.timer`, skip with `--no-update`) rebuilds and restarts only when something changed. HTTPS is
opt-in with `--https`: the installer prints the five risks below, you type `yes` (or pass `--accept-ca-risk`), and only then
runs `fanfare-local.py --issue-certs`. **Fanfare Studio (voice server) is not recommended on a Pi**: too slow. Prepare voices on a laptop and import them.

## With Fanfare Studio (the local voice server)

```sh
docker compose -f compose.yaml -f compose.studio.yaml up -d --build
```

This also builds and runs Fanfare Studio (CPU, ONNX 4-bit; the first start downloads about 3 GB of
models into a volume) from the folder in `FANFARE_STUDIO_DIR` (default `../fanfare-studio`). Until that
repository is renamed it still lives in `../sports-caller-voice-server`:
`FANFARE_STUDIO_DIR=../sports-caller-voice-server docker compose -f compose.yaml -f compose.studio.yaml up -d --build`.

- Studio is published on `127.0.0.1:5123` only, and the page may use it from `http://localhost:<FANFARE_PORT>`.
  With HTTPS add `FANFARE_STUDIO_EXTRA_ORIGINS=,https://fanfare.local:8443`.
- It is reachable from a browser **on this computer** (Fanfare step 4 > Local voice server > Connect,
  `http://127.0.0.1:5123`). Prepare the clips there, export the zip, import it on the phone: see
  `docs/local-voice-server.md`.
- GPU variants (ROCm `/dev/kfd` + `/dev/dri`, NVIDIA `gpus: all`) are described in `compose.studio.yaml`;
  they are not tested in this setup.

## Multi-architecture images (Intel/AMD and ARM)

The build stage always runs on the build machine (the site is plain files, the same on every CPU); the final Caddy
stage exists for each target. Targets: `linux/amd64` and `linux/arm64` (Raspberry Pi 4/5 with the 64-bit OS, Apple
silicon) and `linux/arm/v7` (older Pis with a 32-bit OS; Caddy publishes that image and CI builds it, but it is
not tested on real hardware). Build for another CPU with QEMU:

```sh
docker buildx build --platform linux/amd64,linux/arm64,linux/arm/v7 .               # check that all build (nothing is pushed)
docker buildx build --platform linux/arm64 --load -t fanfare:local .      # an arm64 image for a Pi, then:
docker save fanfare:local -o fanfare-arm64.tar                            # copy to the Pi: install.sh --image-tar fanfare-arm64.tar
```

Continuous integration builds both platforms without pushing. Publishing images to a registry is a manual
decision of the maintainers and is not automated.

## Updating, backups, uninstalling

```sh
git pull
docker compose up -d --build
```

Only changed layers are rebuilt; the voices come from the build cache. Remove old images with
`docker image prune`. The Raspberry Pi appliance does this weekly by itself (`fanfare-update.timer`); run
`sudo /usr/local/sbin/fanfare-update` to do it now.

**Backups: there is nothing to back up.** Teams, lineups and recordings live in each person's browser (use *Export (zip)* in the app).
On the server, only the configuration (the files in `deploy/`, your `.env`) and, if you chose HTTPS, the certificate
folder and the CA in `~/.config/fanfare-local/` (Pi: `/var/lib/fanfare`) are worth keeping.

**Uninstalling:** Docker setups: see "Removing everything" below. Pi appliance: `docker compose --project-directory deploy/raspberry-pi down -v`,
`sudo systemctl disable --now fanfare-update.timer`, delete `/usr/local/sbin/fanfare-update`, `/etc/systemd/system/fanfare-update.*`
and `/var/lib/fanfare` (after `--forget-ca`). Unattended-upgrades and the log limits are harmless; remove them with the files
`52fanfare-unattended-upgrades` and `20auto-upgrades` in `/etc/apt/apt.conf.d/` and `/etc/systemd/journald.conf.d/fanfare.conf`.

## Removing everything

```sh
docker compose down -v          # container, network and the caddy-data volume (Let's Encrypt data)
docker rmi fanfare:local        # the image (add -f compose.studio.yaml for Studio and its volumes)
docker builder prune            # the voice download cache (Podman: podman system prune --build)
```

## Privacy

- No access logs. Caddy's request log is off, its own log is limited to warnings, and the error log
  (`http.log.error`, which would carry the client address and User-Agent) is excluded, so there are no
  addresses, user agents or paths in `docker compose logs`. Server errors are not logged either; to debug,
  temporarily remove `exclude http.log.error` from the Caddyfiles in `docker/` (and rebuild).
  `tests/docker/smoke.sh` checks this for ordinary requests; the error case is not covered by a test.
- No other origin is contacted. The Content-Security-Policy is sent as an HTTP header and is identical
  to the one in `index.html` (the smoke test compares them), allowing only the page's own origin and the
  local voice server on `localhost`/`127.0.0.1`.
- The container runs as an unprivileged user with a read-only root filesystem, all capabilities dropped
  and `no-new-privileges`.
- If you put a reverse proxy in front, its logs are your responsibility. Every example under `deploy/` has them off.

## Tests

`tests/hosting/validate.sh` (reverse-proxy examples) and `tests/raspberry-pi/dry-run.sh` (installer `--dry-run` in Debian bookworm, arm64 through QEMU where available; the Pi compose file with curl checks); both run in CI.

`tests/docker/smoke.sh` builds the image, starts it and checks status codes, the CSP header, MIME types
(`.wasm`, `.onnx`), caching, compression, hardening and the absence of log lines, then the HTTPS mode with a
temporary CA (certificates, risk gate, host check), then runs `down -v`.
It finds `docker compose`, `docker-compose`, `podman compose` or `podman-compose` by itself
(override with `CONTAINER_CLI`) and picks a free port.
